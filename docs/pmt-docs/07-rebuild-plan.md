# 재구축 순서와 설계 변경 기록

## 이번 변경의 범위

2026-10-02 사용자 요청에 따라 AGENTS와 참조 설계를 재작성했다. 아래는 이번 문서에서 정한 재구축 기본안이며, 기존 요구사항 원문에 이 기술 선택이 모두 있었다는 뜻은 아니다. 애플리케이션 파일 이동·의존성 설치·기존 코드 삭제·VM 배포는 아직 수행하지 않았다.

| 결정 | 기존 방식 | 새 기준·이유 |
| --- | --- | --- |
| A01 | `.ctx`의 T번호를 자동 연쇄 실행, planner/executor 고정 | 사용자 작업 범위와 PMT 완료 기준으로 진행. 구 목록 자동 재개 중단 |
| A02 | `web/`, `server/` 별도 패키지 | `apps/`·`packages/` workspace. 계약·클라이언트 공통 코드를 명시적으로 공유 |
| A03 | 순수 DOM, 수제 HTTP 라우터 | React·Fastify. 기능 UI와 서버 공통 처리를 분리 |
| A04 | TypeScript를 Node에서 직접 실행, 의존성 추가 금지 | strict 타입 검사·JS 빌드·근거 있는 의존성 추가. 운영 산출물과 개발 도구 분리 |
| A05 | `web/src/types.ts`가 계약 원천 | contracts의 실행 스키마·타입·OpenAPI. Android에도 동일 계약 제공 |
| A06 | 비영속 실시간 이벤트 + 메시지 조회 | commit과 outbox를 함께 저장, cursor sync·중복 병합·만료 후 재조회 명시 |
| A07 | 후속 기능 제목만 기록 | files·receipts·retention·notifications의 데이터·권한·호출 책임 지정 |
| A08 | systemd 로그 열람만 안내 | JSON 필드·민감값 제한·journal 회전·감사 DB·백업·복원 기준 지정 |

요구사항이나 큰 설계가 바뀌면 이 표를 지우지 않고 새 결정으로 대체 관계·이유·영향받는 문서를 남긴다. 실제 사용자 승인 여부와 에이전트의 구현 선택을 구분한다.

## 단계별 산출물

실행 가능한 책임 분할과 6-luna 병렬 배정은 [상세계획](11-implementation-plan.md)을 따른다. 이 문서의 P단계는 상위 milestone, 상세계획의 B/C/E/N/O 카드는 구현·검증 책임 단위다.

| 단계 | 구현 범위 | 통과 기준 |
| --- | --- | --- |
| P0: 설계 | 이번 AGENTS·참조 문서 | 요구 매핑·구조·모듈·통신·확장·코딩·운영 기준과 링크 검사 |
| P1: 기반 | workspace·React/Fastify 시작점·contracts·설정·로그·migration·CI | Windows Node 24 및 Node 22 환경 check/build 성공, health·비밀값 마스킹·모듈 경계 시험 |
| P2: 대화 흐름 | dev/메일 인증 port, 사용자·세션·개인/단체·메시지·WSS·sync | 로컬 두 브라우저 왕복, 교차 서버 차단, 디스크 DB 재시작·중복·순서·만료 cursor 시험 |
| P3: 실제 통합 | U01, VM HTTPS·실제 메일 어댑터·배포·백업 | 실제 계정 2개 통신 및 타 서버 계정 차단, 재부팅·복원 성공. 이때 1차 완료 |
| P4: 파일·읽음·보존 | U02·U03, files·receipts·retention·audit 관리자 화면 | 비관리자 차단, 스트림 제한·고아 정리·단조 읽음·삭제 중단 재개·복구 후 만료 적용 |
| P5: 앱·알림 | U04, Windows·Android·notifications | 동일 계약 기능 시험, 허용망 실기기 통신, 종료 상태별 알림 결과·한계 기록 |

P1 전에 [U01~U04](01-requirements.md)의 외부 입력까지 전부 기다릴 필요는 없다. 단, 해당 실환경 판정이나 파괴적 보존 기능은 입력 없이 완료 처리하지 않는다. fake 어댑터는 자동 시험용이고 운영 fallback이 아니다.

## 기존 자산 처리

1. 착수 시 `git status`로 사용자 변경을 확인한다. 이번 문서 작업 시작 때 `web/test/login.test.ts`에 미커밋 변경이 있었다. 미래 작업에서는 상태를 다시 확인한다.
2. P1~P2 동안 기존 `web/`는 비교용 데모로 남긴다. 기존 `format`·`validate`·IME 동작·회귀 시나리오는 새 계약에 맞춰 재사용하되 전체 파일을 무검토 복사하지 않는다.
3. 새 엔트리·검증·README 전환이 완료된 뒤 별도 변경으로 옛 `web/`·`.ctx/`·구 verify 도구를 정리한다. 활성 경로와 검증 진입점은 하나로 맞춘다. 구 요구 원문과 검증 이력은 추적할 수 있게 보존한다.
4. 실제 운영 DB·첨부가 존재하는지 재구축 직전에 확인한다. 있으면 snapshot·변환 도구·건수와 경계 비교·복구 시험을 먼저 준비한다. 기존 DB를 새 빈 DB로 덮어쓰지 않는다.
5. `docs/env.md`의 계정·포트·네트워크와 VM 버전은 과거 실측이다. 현황을 재확인한 결과만 운영 절차에 반영한다. 이번 설계 작성이 환경 변경을 의미하지 않는다.

## 작은 VM의 초기 성능 판정

새 프레임워크가 이 VM에서 충분하다는 주장은 아직 검증하지 않았다. P3의 최소 시험 fixture는 사용자 50명·소켓 50개·대화 100개·메시지 10만 건, 10분간 전체 초당 5건 텍스트 전송이다. 메일 인증 부하는 별도로 측정한다.

초기 통과 목표: 서버 RSS 400 MiB 이하, 메시지 HTTP p95 500ms 이하, 연결된 참여자 이벤트 p95 1초 이하, 중복 저장·기록 손실 0건, 미처리 outbox가 부하 종료 뒤 해소됨. CPU·swap·WAL·로그와 백업 공간도 함께 기록한다. 이는 사용자 원문 수치가 아닌 재구축 검증 기준이다.

미달하면 측정한 병목부터 쿼리·인덱스·배치·큐 상한을 조정한다. DB worker나 별도 DB는 그다음에 판단한다. 파일·기기 알림 도입 때 fixture와 용량 계획을 추가한다.

## 종료 알림 판정

공식 플랫폼 자료는 [S10~S13](08-official-references.md)을 참조한다. 창 닫기·트레이 상주·백그라운드·OS에 의한 종료·사용자 강제 중지·재부팅·오프라인을 구분하여 Windows/Android 실기기에서 시험한다. 트레이 상주나 foreground service를 프로세스 종료 상태 성공으로 기록하지 않는다.

우선순위는 외부 중계 없는 방식 검토 → 전원·백그라운드·망 제약 확인 → 요구 충족 여부 기록이다. 종료 상태가 충족되지 않으면 상주 방식 허용 또는 OS 푸시 경로 허용 여부를 사용자와 결정한다. 비용 0원, 강제 중지 후 배달, 닫힌 사설망 접근을 추정으로 보장하지 않는다.
